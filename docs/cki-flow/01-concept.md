# 01. Общая концепция и принципы

## 1.1. Проблема

Команда ЦКИ управляет разработкой через большую физическую/визуальную доску:

- кварталы, спринты, backlog, roadmap;
- User Story, этапы работ, ответственные, статусы;
- зависимости, сроки, релизы, распределение задач.

Доска поддерживается **вручную**. Любое изменение требует правок множества элементов.

Следствия:

| Боль | Почему возникает |
|------|------------------|
| Неактуальность | Данные живут в представлении, а не в модели |
| Дорогое перепланирование | Сдвиг спринта/квартала = каскад ручных правок |
| Слепые зависимости | Связи существуют «в голове» и на стикерах |
| Нет capacity | Невозможно быстро посчитать загрузку ролей |
| Нет прогноза | Риски и сроки не вычисляются из графа работ |
| Нет контроля квартала | Нет единого сигнала «квартал под риском» |

**Вывод:** проблема не в «плохой доске». Проблема в том, что доска *является* системой учёта. Нужно инвертировать отношение: данные → представления.

---

## 1.2. Продуктовое видение

**CKI Flow** — операционная система продуктовой разработки команды ЦКИ.

Пользователь ежедневно:

1. Создаёт и уточняет User Story.
2. Получает автоматически сгенерированный конвейер работ по шаблону.
3. Планирует спринт и квартал с живым capacity.
4. Видит блокировки, критический путь и риски.
5. Управляет релизом как срезом готовых Story, а не как отдельной «колонкой».

Система должна ощущаться как **инструмент принятия решений**, а не как система тикетов.

---

## 1.3. Чем CKI Flow не является

| Не является | Почему |
|-------------|--------|
| Клоном Jira | Jira универсальна и перегружена; ЦКИ нужны узкие процессы и скорость |
| Клоном Linear | Linear оптимизирован под issue velocity; у ЦКИ сильный анализный конвейер и квартальная дисциплина |
| Цифровой копией текущей доски | Копирование доски воспроизведёт ту же боль |
| Документооборотом | Документы — вложения/ссылки, не центр модели |
| HR/табельницей | Capacity учитывает доступность, но продукт не заменяет табель |

---

## 1.4. Главная цель

Сделать управление **кварталом → спринтами → бэклогом** максимально:

- **быстрым** — изменение плана без каскада ручных правок;
- **прозрачным** — один источник истины для статусов, владельцев, зависимостей;
- **предсказуемым** — capacity, критический путь, сигналы риска.

---

## 1.5. Основные принципы системы

### P1. Object-first, view-second

Источник истины — объекты и связи.  
Board / Roadmap / Backlog / Capacity / Release board — проекции.

> Если объект нельзя однозначно описать вне доски — модель ошибочна.

### P2. User Story — атом поставки ценности

Всё планирование, capacity, зависимости и релизы сходятся к User Story.  
Работы (анализ, разработка, тест) — производные от Story и шаблона процесса.

### P3. Процесс как данные (Process-as-Data)

Последовательности работ не зашиты в код.  
Они описываются шаблонами (`Process Template`), версионируются и применяются при создании Story.

### P4. Ортогональные измерения планирования

Иерархия ценности ≠ время ≠ поставка ≠ команда.

```
Ценность:     Goal → Initiative → Epic → Story → Work
Время:        Quarter → Sprint (и Calendar)
Поставка:     Release / Milestone
Организация:  Product → Team → Employee → Role Skill
```

Смешение этих осей в одну «лесенку» — главная ошибка board-систем.

### P5. Автоматизация связей по умолчанию, ручное — по исключению

При создании Story система:

- создаёт Work Items из шаблона;
- строит зависимости между этапами;
- предлагает оценки и роль-исполнителей;
- валидирует конфликты с capacity и сроками.

Ручная правка разрешена, но с явным override и аудитом.

### P6. Предсказуемость важнее полноты полей

Лучше меньше сущностей, но с жёсткими инвариантами и вычисляемыми метриками, чем «ещё 40 custom fields».

### P7. Масштабируемость без переписывания

Новые процессы, роли, типы задач, команды и продукты добавляются конфигурацией (метамодель), а не релизной разработкой ядра.

### P8. Soft constraints + Hard constraints

- **Hard:** циклы зависимостей, Story в двух активных спринтах, удаление Epic с активными Story без стратегии.
- **Soft:** перегруз capacity, Story без оценки, релиз без QA-завершения — предупреждения, не блокировки (или блокировки по политике).

## 1.6. Улучшение исходной иерархии (критично)

### Исходное предложение

```
Цель квартала → Инициатива → Epic → User Story → Работы → Release → Done
```

### Проблемы

1. **Release** — не ребёнок Story и не этап после работ. Это срез поставки (многие Story → один Release; Story может жить без Release).
2. **Done** — статус, не объект иерархии.
3. Нет уровня **Product** — при появлении второго продукта модель ломается.
4. Нет явного места для **Sprint** — он не «между» Story и Work.

### Рекомендуемая иерархия ценности

```
Product
 └─ Quarter
     └─ Quarter Goal (OKR / целевой исход)
         └─ Initiative (продуктовая ставка квартала)
             └─ Epic (крупный результат)
                 └─ User Story (атом ценности)  ← ЦЕНТР
                     └─ Work Item (этап/работа из шаблона)
```

### Ортогональные связи (не иерархия)

| Измерение | Объекты | Связь с Story |
|-----------|---------|---------------|
| Время исполнения | Sprint | Story / Work Item ∈ Sprint (assignment) |
| Поставка | Release, Milestone | Story ∈ Release (membership) |
| Организация | Team, Employee, Role | assignee / capacity reservation |
| Классификация | Label, Priority, Component | tags / ranking |

**Преимущества:**

- перепланирование спринта не ломает иерархию ценности;
- релиз можно собирать независимо от структуры Epic;
- capacity считается по ролям Work Item, а не «по карточке на доске»;
- Done остаётся статусом на каждом уровне, а не «финальной папкой».

## 1.7. UX-стратегия (без UI-кода)

Продукт должен поддерживаться годами. UX-принципы уровня стратегии:

1. **Один объект — один «дом».** Карточка Story открывается одинаково из board, roadmap, sprint, release.
2. **Планирование = манипуляция графом**, а не перетаскивание стикеров как единственный способ.
3. **Сигналы важнее таблиц.** «Квартал под риском», «критический путь сдвинут», «QA перегружен на 140%» — первичный UX.
4. **Скорость создания Story.** Цель: от идеи до полного конвейера работ — < 60 секунд (шаблон + минимум полей).
5. **Доска остаётся**, но как view «Sprint Board» / «Quarter Board», синхронизированный с моделью.

---

## 1.8. Критерии успеха продукта

| Метрика | Целевое поведение |
|---------|-------------------|
| Time-to-replan sprint | Перенос Story между спринтами с автопересчётом capacity и зависимостей |
| Freshness | Статус Story/Work обновляется исполнителями; доска не требует отдельного «обслуживания» |
| Risk visibility | Риск квартала виден без ручной аналитики |
| Template coverage | ≥ 80% новых Story создаются из шаблона |
| Adoption | Ежедневное использование PM, BA, SA, Dev, QA без параллельной «теневой» доски |

---

## 1.9. Границы MVP vs долгосрочная модель

Архитектура описывает **целевую** модель. Для реализации позже допускается вертикальный срез:

**MVP (логический, не кодовый):** Product + Quarter + Initiative + Epic + Story + Work + Sprint + Process Template + Dependency + Capacity по ролям + одна board-проекция.

**Отложено:** мультипродукт с федерацией, сложные portfolio-roadmap на годы, интеграции с внешними трекерами, AI-прогноз сроков.
