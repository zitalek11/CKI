# 10. Альтернативные архитектуры и обоснование выбора

## 10.1. Критерии сравнения

Для команды ЦКИ важны:

1. Скорость перепланирования квартала/спринта.
2. Честный учёт аналитического конвейера (BA→SA→Dev→QA).
3. Capacity по ролям, не только SP.
4. Автозависимости из процессов.
5. Долговечность (годы использования) и расширяемость.
6. Отказ от ручного «обслуживания доски».
7. Разумная сложность внедрения.

---

## 10.2. Альтернатива A — Board-Centric Digital Twin

**Суть:** оцифровать текущую доску 1:1 (колонки, карточки, кварталы как секции).

| Плюсы | Минусы |
|-------|--------|
| Быстрый emotional buy-in | Данные = представление; та же боль актуальности |
| Минимум обучения | Перепланирование остаётся ручным каскадом |
| | Capacity/critical path почти невозможны честно |
| | Масштабирование = ещё больше колонок |

**Вердикт:** анти-цель. Повторяет проблему.

---

## 10.3. Альтернатива B — Classic Issue Tracker (Jira-like)

**Суть:** Issue + Epic + Sprint + Workflow statuses + board.

| Плюсы | Минусы |
|-------|--------|
| Зрелая ментальная модель | Универсальность → конфигурационный ад |
| Много интеграций | Слабая native модель process templates для BA→SA→… |
| | Capacity часто plugin/вторичен |
| | Легко вернуться к «тикетам ради тикетов» |

**Вердикт:** можно использовать как инфраструктуру, но **как продукт для ЦКИ** — слишком generic. Мы проектируем специализированный инструмент.

---

## 10.4. Альтернатива C — Story-only Kanban (Linear-like)

**Суть:** плоский поток Issue/Story, минимум иерархии, скорость исполнения.

| Плюсы | Минусы |
|-------|--------|
| Отличный UX скорости | Слабый quarter portfolio слой |
| Мало сущностей | Аналитический конвейер не first-class |
| | Ролевая capacity обычно вторична |

**Вердикт:** отличный UX-референс для Story Workspace, но недостаточная модель планирования ЦКИ.

---

## 10.5. Альтернатива D — Pure Hierarchy PPM (Goal→…→Task→Release→Done)

**Суть:** всё в одной лесенке, включая Release и Done как уровни (исходное предложение).

| Плюсы | Минусы |
|-------|--------|
| Просто объяснить | Release/Done ломают модель (это не children Story) |
| | Sprint некуда положить «правильно» |
| | Перепланирование поставки связано с перестройкой дерева |

**Вердикт:** иерархия ценности нужна, но Release/Sprint/Done должны быть ортогональны.

---

## 10.6. Альтернатива E — Object Graph + Orthogonal Timeboxes + Process Templates (**выбрано**)

**Суть (CKI Flow):**

- иерархия ценности: Product → QuarterGoal → Initiative → Epic → UserStory → WorkItem;
- ортогонально: Sprint, Release, Team/Role Capacity, Calendar;
- Process Templates генерируют работы и зависимости;
- Dependency/Scheduling/Capacity engines считают риски и загрузку;
- Board/Roadmap/Backlog — проекции.

| Плюсы | Минусы / цена |
|-------|----------------|
| Устраняет ручное обслуживание доски | Выше концептуальная сложность на старте |
| Честный конвейер ролей ЦКИ | Нужен Template Engine и Capacity Engine |
| Быстрый replan с пересчётом | Требует дисциплины DoR/шаблонов |
| Масштабируется конфигурацией | Нельзя «просто нарисовать колонки» и закончить |
| Долговечная модель данных | Обучение команды новой ментальной модели |

**Вердикт:** лучший fit для главной цели — предсказуемое управление кварталом/спринтами/бэклогом.

## 10.7. Частные альтернативы внутри выбранной модели

### E1. Eager vs Lazy vs Hybrid создание работ

| | Eager | Lazy | **Hybrid (выбор)** |
|---|-------|------|---------------------|
| Видимость capacity | высокая | низкая | высокая |
| Шум UI | высокий | низкий | средний (с collapse) |
| Предсказуемость квартала | высокая | слабая | высокая |

### E2. Feature между Epic и Story

| | Всегда Feature | **Опциональный Feature (выбор)** | Никогда |
|---|----------------|----------------------------------|---------|
| Гибкость | низкая | высокая | средняя |
| Лишние клики | часто | редко | нет |
| Сложность | выше | конфигурируемая | ниже |

### E3. Story целиком в одном спринте vs split WorkItems

| | Story-only sprint | **Split WorkItems (выбор)** |
|---|-------------------|-----------------------------|
| Простота | выше | ниже |
| Честность для BA→QA | низкая | высокая |
| Соответствие ЦКИ | слабое | сильное |

### E4. Checklist stages vs WorkItem stages

Выбраны **WorkItems** (см. документ 04) ради capacity и assignees.

### E5. SP-only capacity vs Role-hours capacity

Выбрана **трёхслойная модель** (Role pools + People + SP auxiliary) — документ 07.

## 10.8. Итоговое решение

**Принятая архитектура:** Alternative E — **Object Graph + Orthogonal Timeboxes + Process Templates**, с Hybrid генерацией работ, опциональным Feature, split WorkItems across sprints, role-based capacity и projection-based boards.

### Почему это лучше исходной идеи «доска → объекты»

Исходная боль команды — следствие board-as-source-of-truth.  
Выбранная модель делает доску дешёвой проекцией и переносит стоимость изменений на автоматические движки (template/dependency/capacity/scheduling).

### Почему это лучше «просто внедрить Jira»

Jira решает универсальный issue tracking.  
ЦКИ нужна операционная система квартального планирования с аналитическим конвейером. Специализация здесь — преимущество на годы, не ограничение.

---

## 10.9. Риски выбранной архитектуры и митигации

| Риск | Митигация |
|------|-----------|
| Over-modeling | Жёсткий MVP-срез сущностей; Feature/WSJF/внешние интеграции — позже |
| Сопротивление шаблонам | 5 стартовых шаблонов под реальные типы работ ЦКИ; отклонение шаблона разрешено, но видно |
| Сложная capacity | Начать с role pools на sprint; personal optimization — второй шаг |
| Желание вернуться к «просто доске» | Board view с первого usable slice, но запись только через объекты |
| Ошибки в critical path | Сначала hard FS + calendar days; сложные SS/FF — постепенно |
